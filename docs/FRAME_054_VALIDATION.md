# FRAME 0.5.4 Beta validation (recording UX, game detection, Library and editor fixes), 2026-10-13

Not packaged or published. Recording pipeline, encoder settings, audio and FFmpeg timing code are unchanged (no edits to Backend.cs, CaptureCoordinator.cs, MediaExport.cs, AudioPipe.cs, AudioDevices.cs). FRAME Advanced is unaffected (none of the changed files are linked into it).

## Root causes
1. **Library ••• menu looked empty.** The app-wide implicit `TextBlock` style sets `Foreground = Text` (#F5EEE6 in the dark theme). Code-built `ContextMenu`s used WPF's default light menu chrome, so the menu item labels were near-white on a near-white popup. Items, bindings and sizing were fine. Fix: themed `ContextMenu`, `MenuItem` and menu `Separator` styles in App.xaml (Surface background, Text foreground, Raised + Accent highlight). Measured in the UI test: every label > 20 px wide with a luminance gap > 0.45 to the menu background.
2. **Trim editor "Save clip" seemed to do nothing.** A trimmed range is always re-encoded, and since 0.4.0 the editor refused re-encoding while any capture ran (`captureBusy()`), returning early with only a small grey status line and no log. With Shadow Recording on (the normal state) every Save clip was refused. The button binding and export pipeline worked. Fix (user decision 2026-10-13, "low-impact CPU"): while capture runs the export still starts, with CPU libx264 (same CRF quality), process priority Idle and at most two threads (`-threads 2`, `-filter_complex_threads 1`), so the capture encoder keeps the GPU. Not running capture: unchanged (probed hardware H.264, BelowNormal). Every failure now shows in the editor, writes `trim` to diagnostics.log and shows a top-right note; the catch is no longer filtered, so an unexpected exception cannot vanish.
3. **No feedback after the Save Replay hotkey.** The only note came after the export and ffprobe check (≈1–5 s or more). Requests that hit a busy FRAME were dropped with an in-window status line only.

## Implemented
- **Replay save notes** (`MainWindow.RequestSaveReplay`, single entry for hotkey, button, tray and toolbar): accepted request → "Saving replay… · Processing your clip" (gold open ring, `SaveOverlay.Pending`) before any waiting; then "Clip saved · Last N … saved" (measured length) or "Replay not saved · reason". Same overlay instance, text swapped in place (no stacking or flicker). A press while a save runs → "Still saving replay…" (the running save continues; no second export); a press while another action runs → "Replay not saved · FRAME is busy · try again in a moment". `ShowSaveNotifications` still controls these notes. Save timing, priority and export pipeline unchanged.
- **Game-aware minimize** (`GameMinimize.cs`, Core `GameDetection`/`GameMinimizePolicy`): reuses the existing `EVENT_SYSTEM_FOREGROUND` WinEvent hook of `ReplayGameTracker` (out-of-context, no injection). On each foreground change: one process-name query. A game = a known executable (`GameCatalog` + a detection-only list, routing unchanged) or, for unknown programs, Windows' own `SHQueryUserNotificationState == QUNS_RUNNING_D3D_FULL_SCREEN` checked once 2.5 s after the switch (one-shot timer). Browser/video fullscreen (`QUNS_BUSY`) never counts. Hide = the same Hide-to-tray as the close button (capture, hotkeys, tray continue; decorative timer stops). Each game process is handled once: reopening FRAME while that game runs never hides it again. Not hidden when an editor/dialog/other FRAME window is open, a hotkey is being recorded, or there was input in FRAME in the last 2 s. Setting **Settings → General → Games: "Minimize FRAME when a game starts"** (`MinimizeOnGameStart`, default on, legacy files on), saves immediately (also while recording). Logged as `game-minimize`.
- **Library menu**: Play clip, Show in folder, Copy file path, Rename, Copy file, separator, Delete clip (Delete image for PNG). Opens below the ••• button and focuses the first item (keyboard). Delete: confirmation naming the file and folder (default No) → Recycle Bin; a locked or read-only file is detected first (FRAME message instead of a blocking shell dialog); success only when the file is really gone; list refreshed.
- **Save clip**: `<OutputDirectory>\Trimmed Clips\` (`ReplayFolders.TrimmedClips`), created on first save; name `FRAME <date time> <source name> · clip.mp4` reserved with CreateNew (never overwrites); status "Saving clip…" immediately, progress bar, "Saved · name · in Trimmed Clips", top-right "Clip saved" note; Library refreshes (file listing only; thumbnails/probes are cached per file).
- **Save to…**: native Save As (`Microsoft.Win32.SaveFileDialog`, files and folders visible, "MP4 video" + "All files", default name `<source> clip.mp4`, overwrite prompt). Starts in the last successful Save to… folder (`TrimSaveDirectory`, persisted) if it exists, else Trimmed Clips, else the recording's folder. Cancel = no export and no settings change. Replacing a file only after the Windows prompt confirmed it, only after the new file was verified, and never the source recording. Save clip never uses the remembered folder.
- **Library**: also lists regular `.mp4` files directly in `Trimmed Clips` (no links, no nested folders; tag "TRIMMED CLIPS"). Game folders unchanged.
- Version 0.5.4 (`Frame.App.csproj`).

## Detection limitations (by design)
Only known executables and Direct3D exclusive-fullscreen apps count. Borderless-windowed games not in the list are not detected (most modern games default to borderless). Games running elevated may hide their executable name (OpenProcess denied) and then only the fullscreen signal can match. Extend `GameDetection` (detection only) or `GameCatalog` (also creates replay folders) with confirmed executable names.
